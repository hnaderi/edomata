# Wire compatibility

The Rust port keeps the on-disk formats of the Scala library. Scala and Rust services can share
one PostgreSQL database, and a migration from one language to the other can be gradual: a Rust
process resumes where a Scala one stopped, and the reverse.

## What is shared

- **Tables and DDL.** `PGSchema` and `SaaSPGSchema` generate byte-for-byte the same statements in
  both languages, for both naming strategies (`PGNaming::schema`, which gives `"ns".journal`, and
  `PGNaming::prefixed`, which gives `ns_journal`) and for every payload type. Golden tests compare
  the Rust output with files generated by the Scala code.
- **Queries.** The sqlx driver issues the same queries as the Skunk and Doobie drivers: same
  columns, ordering, upserts, and the same handling of unique violations, which become a
  `VersionConflict`.
- **Journal, outbox, commands, snapshots and migrations** use the same tables and the same rows, so
  events, pending outbox items, processed command ids and snapshots written by one language are
  read by the other.
- **Payloads** are `jsonb` by default, written in the native PostgreSQL binary format like the
  Scala codecs. `SerdeCodec::json()` and `SerdeCodec::bytea()` store `json` and `bytea` columns
  instead; a `bytea` payload holds compact JSON bytes, like the one jsoniter-scala's `msgpack`
  codec writes.

A cross-language test proves it on a real database: the Scala side writes events, commands,
outbox items and a snapshot, the Rust side reads them and appends, and the Scala side verifies
the result
([`cross_language.rs`](https://github.com/beyond-scale-group/edomata/blob/main/rust/crates/edomata-e2e/tests/cross_language.rs)).

The Rust port adds a table the Scala library does not have: `relay_checkpoints`, used by the
journal relay of `edomata-broker`. `PGSchema::eventsourcing` does not include it, so its output
stays identical to Scala's; append `PGSchema::relay_checkpoints` when you stream the journal.

## Matching the JSON shape

Rust reads the payloads written by the Scala Circe, jsoniter-scala and uPickle JSON codecs,
provided the Rust types serialize to the same JSON shape. Golden payload tests check each codec:

| Scala codec | serde representation |
|-------------|----------------------|
| Circe generic derivation | externally tagged (serde's default); use struct variants everywhere, including parameterless cases (`Opened {}` is written `{"Opened": {}}`) |
| jsoniter-scala `JsonCodecMaker.make` | `#[serde(tag = "type")]`; `Option` fields with `#[serde(default, skip_serializing_if = "Option::is_none")]` |
| uPickle `ReadWriter.derived` | `#[serde(tag = "$type")]` in an untagged wrapper, since parameterless cases are bare strings; `Option` fields with `edomata_serde::compat::upickle_option` |

Use `#[serde(rename_all_fields = "camelCase")]` (or per-field `rename`) for camelCase field
names, and `rust_decimal::Decimal` with `rust_decimal::serde::float` for `BigDecimal` fields,
which are JSON numbers.

jsoniter-scala's `msgpack` codec writes JSON bytes despite its name, so its `bytea` payloads are
readable too.

## Known limitation: uPickle MessagePack

Payloads written by uPickle's `msgpack` codec are real MessagePack in `bytea` columns. The Rust
port **cannot read them**, because `serde_json` is its only serializer, and an event migration
cannot convert them either, since it works on JSON text. Migrate such journals to a JSON codec on
the Scala side before sharing them with Rust services, or keep them on the Scala side.
