# Schema management

Edomata's tables are ordinary PostgreSQL tables. They can be created by the drivers at start-up (the default, convenient for development) or by a migration tool such as Flyway or Liquibase (usual in production, where the application role often cannot run DDL). The code of this chapter is in `rust/book/samples/src/operations.rs`.

## What creates what

| Step | DDL executed (automatic setup) | With `skip_setup = true` |
|------|--------------------------------|--------------------------|
| `SqlxDriver::new` / `for_namespace` / `new_with` | `CREATE SCHEMA IF NOT EXISTS` (schema naming only) | nothing |
| `Backend::builder(..).driver(driver)...build()` | `journal`, `outbox`, `commands` tables and their indexes (CQRS: `states`, `outbox`, `commands`) | nothing |
| `persisted_snapshot(codec)` | the `snapshots` table, when the backend is built | nothing |
| `SqlxMigrations::run` | the `migrations` table | the `migrations` table (always) |
| `PgCheckpointStore::setup` (`edomata-broker`) | the `relay_checkpoints` table | not affected by the driver's flag |

Every statement is `CREATE ... IF NOT EXISTS`, so automatic setup is idempotent. The drivers run their DDL in transactions that take a PostgreSQL advisory lock shared by every Edomata driver, so several replicas starting at once do not collide on `CREATE TABLE`.

## Generating the DDL

`PGSchema` returns the statements the drivers would run, byte-for-byte identical to the Scala library's `PGSchema` (golden files generated by the Scala code are asserted in CI):

| Function | Tables |
|----------|--------|
| `PGSchema::eventsourcing(&naming)` | `journal`, `outbox`, `commands`, `snapshots`, `migrations` (`jsonb` payloads) |
| `PGSchema::eventsourcing_with(&naming, event, notification, snapshot)` | the same, with explicit payload types |
| `PGSchema::cqrs(&naming)` / `cqrs_with(&naming, state, notification)` | `states`, `outbox`, `commands` |
| `PGSchema::relay_checkpoints(&naming)` | `relay_checkpoints`, for a `JournalRelay` (not part of `eventsourcing`, to keep that output identical to Scala's) |
| `SaaSPGSchema::cqrs_with(&naming, state, notification, rls)` (`edomata-saas`) | tenant-aware `states`, `outbox`, `commands`, optional Row-Level Security |

In schema naming the first statement is `CREATE SCHEMA IF NOT EXISTS`; prefixed naming creates no schema and prefixes constraint and index names too (`accounts_journal_pk`), so several aggregates can share one schema. Payload types are spliced into the DDL as given: use `"jsonb"` (the default), `"json"` or `"bytea"`, and the same format as the codecs of the backend.

## A Flyway workflow

1. Generate the migration file once, with a small program or a test:

   ```rust,ignore
   {{#include ../../samples/src/operations.rs:flyway_file}}
   ```

   Save the output as `src/main/resources/db/migration/V1__create_accounts_tables.sql` (or wherever your Flyway configuration looks), and commit it. Later versions of Edomata keep the same DDL; the golden tests guarantee it.

2. Build the drivers with `skip_setup = true`, so that the application never runs DDL. At start-up, run the pending event migrations before the backend handles commands:

   ```rust,ignore
   {{#include ../../samples/src/operations.rs:startup}}
   ```

3. When adding an aggregate, generate its tables with its own namespace and add a new Flyway version; never edit an applied one.

`SimplePGSchema` gives the same statements to `edomata-simple` users ([Simple API](../backends/simple-api.md#ddl-for-migrations)).

## Sharing the database with Scala services

Scala and Rust services can use the same tables: same naming strategy and namespace, same payload type. Tables created by the Scala drivers, by Flyway from the Scala `PGSchema` or from the Rust one are identical. See the [migration guide](../other/migration-guide.md#sharing-a-database).
